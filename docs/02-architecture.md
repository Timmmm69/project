# Architecture

## Выбранный подход

Проект строится как Next.js монолит:

- публичная часть;
- админка;
- API routes / server actions;
- общая бизнес-логика;
- Prisma-доступ к PostgreSQL.

Это проще для MVP: один репозиторий, один deployment, меньше инфраструктуры и меньше связей между сервисами.

## Основные слои

- `src/app`: страницы, layouts, API endpoints.
- `src/features`: бизнес-модули по доменам.
- `src/server`: серверные общие части: database, auth, events.
- `src/lib`: общие утилиты без доменной логики.
- `prisma`: схема базы.
- `docs`: источник истины и рабочая документация.
- `tests`: unit и e2e проверки.

## PaymentProvider

Оплата проектируется через adapter:

- бизнес-логика знает только общий интерфейс оплаты;
- конкретный провайдер Беларусь-first подключается внутри adapter;
- webhook проверяется на backend;
- сумма, валюта и id платежа проверяются на backend;
- повторный webhook не создает второй Access.

До Sprint 5 нужно выбрать точный провайдер: bePaid, WebPay, ЕРИП/E-POS или другой.

## Access lifecycle

Access создается только из трех источников:

- подтвержденная оплата;
- ручная выдача админом;
- валидный одноразовый код.

Перед стартом теста backend проверяет access, срок действия, количество попыток и наличие started attempt.

## Attempt lifecycle

При старте теста в одной transaction:

- создается Attempt;
- создается snapshot теста, вопросов, ответов, баллов, тем и шкалы;
- `attempts_available` уменьшается на 1.

Если ученик обновил страницу, backend возвращает текущую `started` попытку без повторного списания.

## Scoring

Scoring выполняется только на backend.

Frontend не должен:

- решать, есть ли доступ;
- считать итоговый балл;
- получать правильные ответы до завершения.

## Security baseline

- Админка защищена авторизацией.
- Пароль админа хранится как hash.
- AccessCode хранится как hash.
- Webhook проверяется.
- Ученик не видит чужой результат.
- Все критические операции выполняются transaction.
