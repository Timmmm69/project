## Цель

Реализовать creating_order, creating_payment_session, redirecting и безопасный 10-second fallback.

## Источники требований

- `docs/payment-program/sources/payment-ux-contract-v1.md` разделы 6.3—6.4

Audit/traceability IDs: `PAY-04`, `PAY-05`, `UI-01`.

## В scope

- Реализовать только цель и критерии этой карточки.
- Сохранить backend truth, idempotency, transaction и privacy invariants.
- Обновить board, evidence и handoff вместе с изменением.

## Вне scope

- Реализация соседних карточек без отдельного claim.
- Production activation или изменение gate verdict.
- Card-data UI, embedded bank form, автоматические возвраты и другие запрещённые MVP-функции.


## Критерии приёмки

- [x] CTA немедленно блокирует повторный submit — `busy` state + `checkoutPhase !== "idle"` блокирует все формы.
- [x] Один checkout_flow создаёт не более одного Order — `checkoutFlowId` ref создаётся один раз, серверный idempotency key + `commercial_order_id_idempotency_key` constraint.
- [x] Existing provider session переиспользуется — `paymentKey` ref один на lifecycle, `Idempotency-Key` header, сервер возвращает existing session при повторном вызове.
- [x] Canonical navigation — same-tab redirect — `document.createElement("form")` + `form.submit()` в той же вкладке.
- [x] Fallback появляется только после подтверждённого session creation и не создаёт новую session — `paymentFormRef.current` устанавливается только после успешного `POST /payment-session`, fallback использует сохранённый ref без повторного API-вызова.

## Evidence

- `src/app/(public)/tests/[slug]/commercial-checkout-form.tsx` — **машина состояний redirect handoff**:
  - **`checkoutPhase` state machine:** `idle` → `creating_order` → `creating_session` → `redirecting` / `fallback` / `session_error`.
  - **`creating_order` phase** — loader «Создаём заказ…» с спиннером, текст «Фиксируем цену, состав покупки и данные для перехода к оплате». CTA заблокирован через `busy` и `checkoutPhase`.
  - **`creating_session` phase** — loader «Открываем защищённую страницу WEBPAY…», текст о redirect и card data boundary.
  - **`redirecting` phase** — «Переходим к оплате…», форма отправляется через POST в той же вкладке (same-tab redirect).
  - **`fallback` phase** — через 10 сек после неудачного `form.submit()`, заголовок «Страница оплаты не открылась автоматически», CTA «Открыть страницу WEBPAY» использует `paymentFormRef` без нового API-вызова.
  - **`session_error` phase** — заголовок «Не удалось открыть страницу оплаты», текст «Заказ сохранён. Перед повторной попыткой мы проверим его состояние, чтобы не создать дубликат.», CTA «Попробовать снова» (вызывает `refreshStatus` → проверяет `allowedActions` перед retry).
  - **Idempotency:** `orderKey`, `checkoutFlowId`, `paymentKey` — refs, создаются один раз, передаются в `Idempotency-Key` header. Серверный constraint предотвращает дубликаты.
  - **No localStorage:** все данные хранятся в памяти (`useRef`). Provider data (WEBPAY fields, payment URL) не попадают в localStorage/sessionStorage/analytics.
  - **Safe errors:** opaque `orderReference` (publicId) в сообщениях. `commercialErrorResponse` на backend отдаёт только allowlisted коды.
