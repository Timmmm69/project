# Русский язык ЦЭ/ЦТ: оценивание v2

Изменение от 04.11.2026 по отдельному заданию владельца. Разрешение на частичные баллы для authentic-режима заменяет прежнее ограничение MVP. Generic, платежи, авторизация, публичный состав результата и таблица 0–100 не меняются.

## Подтверждённая методика и отличие учебного варианта

Источники проверены 04.11.2026:

- [Официальные схемы РИКЗ 2026](https://rikc.by/cctesting/727-shema-nachislenija-pervichnyh-ballov-za-vernoe-chastichno-vernoe-vypolnenie-zadanij-ct.html), PDF за 26/29 мая, страницы 1 и 6–7.
- [Общая схема РИКЗ](https://rikc.by/553-obschaja-shema-nachislenija-pervichnyh-ballov.html), пункты 2, 4, 5.
- [FAQ РИКЗ](https://rikc.by/486-chasto-zadavaemye-voprosy.html), частично верные ответы.
- [Порядок заполнения бланка](https://rikc.by/cctesting/45-zapolnenie-blanka.html).
- [Сопоставление с «Решу ЦТ»](https://rus_ct.sdamgia.ru/manual): перечень B расходится с официальной схемой по B14.

Для наборов одна ошибка — один лишний ИЛИ один пропущенный элемент. Замена — две ошибки. Для соответствий считаются неверные цифры при полной записи и фиксированном порядке букв. Пропущенные/повторные позиции и переставленные пары не соответствуют официальному формату и дают 0.

Официальная схема основного экзамена 2026 допускает частичный балл также за B14. В существующем авторском варианте B14 — словесный термин «лексикология»: сохраняется точное сравнение 2/0. При публикации выдаётся предупреждение `RIKZ_RUSSIAN_B14_AUTHORED_VARIATION`. Для буквального соответствия структуры реальному экзамену необходима методическая замена содержания B14; она не выполнена под видом исправления scoring.

## Формат и совместимость

`partialPolicy` хранит стратегию; `normalizationPolicy` — JSON v1 с типом и явным доменом. В заданиях с иными числовыми доменами их нужно указывать явно: нельзя выводить допустимые цифры из правильного ключа или текста задания. Дефолт существующего пятиальтернативного варианта — 1–5.

Наборы принимают перестановки, регистр, пробелы и одиночные запятые. Это удобство веб-интерфейса, а не разрешение писать разделители на бумажном бланке. Дубликаты и посторонние символы не удаляются: ответ получает 0. Соответствия требуют полной слитной записи кириллицей в порядке А–Б–В–Г. Латинские двойники не подменяются. Обычные токены: trim, NFC, регистр; е/ё различаются, кроме явных альтернатив. Многословный ответ вводится слитно по инструкции бланка. Правильность не оценивается по похожести.

Парсер различает `empty`, `invalid`, `valid`. Пустые/некорректные ответы дают 0; валидные оцениваются выбранной стратегией. Сырой ввод сохраняется без очистки, включая незаконченные и ошибочные значения. Из альтернатив выбирается максимальный результат, сумма за вопрос не превышает 2.

Новые authentic-попытки получают `scoringVersion: 2` и полные политики в snapshot. Пустые/прежние метаданные опубликованных заданий преобразуются только при создании нового snapshot. Уже начатые snapshot без версии сохраняют прежний алгоритм. Завершённые результаты читаются из сохранённых баллов, без пересчёта. Новые схемы БД и миграции не нужны.

Импорт поддерживает прежние колонки и две дополнительные в конце: `partial_policy`, `normalization_policy`. JSON политики не теряется при commit. `accepted_answers` поддерживает альтернативы и для A, и для B. Противоречивые стратегии, домены, подтипы, ключи и максимум не 2 блокируются до публикации; проверка повторяется перед стартом. Старые validated import jobs также проверяются при commit.

Из источников убраны четыре подсказки формата, совпадавшие с matching-ключами. Для ранее опубликованных данных и старых активных snapshot тот же точный известный суффикс скрывается в student projection; сохранённый snapshot и scoring не меняются. Произвольные формулировки не разбираются эвристически.

Сохранение и завершение используют одну блокировку строки attempt внутри transaction. После завершения или deadline запись запрещена. Клиент последовательно сохраняет изменения каждого вопроса, дожидается очередей, повторяет неудавшиеся сохранения и блокирует ввод на время завершения. Таймер использует серверный остаток и монотонные часы; после временной ошибки expiry повторяется с ограничением частоты.

## Проверки

Команды репозитория: `pnpm test`, `pnpm typecheck`, `pnpm lint`, `pnpm build`.

Расширенные проверки:

```bash
# Только выделенная тестовая схема, не production.
DATABASE_URL='postgresql://postgres:postgres@localhost:5432/scoring_test?schema=scoring_v2_ci' pnpm exec prisma migrate deploy
RUN_SCORING_V2_INTEGRATION=true DATABASE_URL='postgresql://postgres:postgres@localhost:5432/scoring_test?schema=scoring_v2_ci' pnpm exec vitest run tests/integration/authentic-scoring-v2.test.ts

# Локальный сервер и Chromium нужны для браузерной проверки.
VERIFIED_COMMERCIAL_SESSION_MODE=off pnpm exec playwright test tests/e2e/authentic-scoring-v2.spec.ts --workers=1
```

В unit-тестах перебраны все 32 подмножества для нескольких ключей, перестановки и все 625 полных соответствий. Есть проверки альтернатив, Unicode, некорректного ввода, реальных 40 вопросов, lookup шкалы, старых snapshot и generic.

Интеграционные тесты используют настоящие validate/commit API, Prisma и сервис попыток. Проверяют 80/80, все 27 частичных заданий, неверный ввод, восстановление, неизменяемость правил, повторное завершение, timer и сохранённый публичный контракт результата. В CI добавлен прогон этой группы на PostgreSQL 16.

Локальная среда: изолированная PGlite, все 17 миграций применены. Она подтверждает последовательный путь Prisma, но не заменяет проверку настоящей конкуренции PostgreSQL. Браузерные тесты подготовлены; исполнение не подтверждено: официальный download Chromium повреждён, временная альтернативная установка отклонена автоматической проверкой разрешений.

Отдельный прежний integration suite `primary-only-authentic-result.test.ts` локально возвращает 403 `VERIFIED_SCOPE_NOT_ALLOWED` на этапе claim-access: 4/4 теста падают также на чистом исходном коммите `69a5419` в той же среде. Ошибка возникает до scoring; авторизация не изменялась. Это ограничение расширенного прогона, а не успешная проверка этого suite.
