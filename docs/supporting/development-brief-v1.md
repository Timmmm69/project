# **ТЗ для разработки v1.1**

## **1\. Назначение документа**

Этот документ описывает техническое задание на разработку первой версии веб\-сервиса онлайн-тестов по русскому языку для подготовки к ЦЭ/ЦТ.

Документ фиксирует:

1. роли пользователей;  
2. основные сценарии;  
3. функциональные требования;  
4. бизнес-правила;  
5. структуру публичной части;  
6. структуру админки;  
7. правила создания тестов;  
8. правила импорта Excel/CSV;  
9. правила оплаты и доступов;  
10. одноразовые коды доступа;  
11. прохождение теста;  
12. расчёт результата;  
13. требования к безопасности;  
14. критерии готовности MVP.

Документ обновлён с учётом MVP v1.1.

---

## **2\. Суть продукта**

Нужно разработать веб\-сервис, где преподаватель может создавать и продавать онлайн-тесты по русскому языку, а ученик может купить доступ, пройти тест и получить результат.

Первая версия продукта должна поддерживать:

1. русский язык;  
2. 1-3 теста на старте;  
3. ручное создание тестов;  
4. импорт вопросов из Excel/CSV;  
5. оплату одного теста;  
6. ручную выдачу доступа;  
7. одноразовые коды доступа;  
8. прохождение теста онлайн;  
9. автоматическую проверку;  
10. результат с баллами, ошибками, правильными ответами и темами.

---

## **3\. Главная цель MVP**

Цель MVP:

Преподаватель может сам создать или загрузить тест, опубликовать его и продать ученику. Ученик может получить доступ, пройти тест и увидеть результат.

Рабочая цепочка MVP:

преподаватель создал тест → добавил вопросы → опубликовал → ученик оплатил или активировал код → получил доступ → прошёл тест → увидел результат → преподаватель увидел оплату/доступ/результат.

4. добавлять вопросы вручную;

6. редактировать вопросы после импорта;  
7. удалять вопросы;  
8. менять порядок вопросов;  
9. запускать предпросмотр теста;  
10. публиковать тесты;  
11. скрывать тесты;  
12. смотреть оплаты;  
13. смотреть доступы;  
14. выдавать доступ вручную;  
15. создавать одноразовые коды доступа;  
16. смотреть результаты учеников.

---

## **4.2. Ученик**

Ученик пользуется публичной частью сервиса.

Ученик может:

7. пройти тест;  
8. увидеть результат;  
9. увидеть ошибки;  
10. увидеть правильные ответы;  
11. увидеть результат по темам.

В первой версии отдельной роли родителя нет.

Если родитель оплачивает тест, технически доступ всё равно привязывается к email, указанному при покупке или активации.

## **5\. Предмет и режимы тестов**

## **5.1. Предмет первой версии**

В первой версии поддерживается:

1. русский язык.

При этом архитектура должна позволять добавить другие предметы в будущем. Для этого у теста должно быть поле `subject`.

---

## **5.2. Режимы теста**

В первой версии нужны два режима теста:

1. тренировочный режим;  
2. режим ЦЭ/ЦТ.

### **Тренировочный режим**

В тренировочном режиме результат считается по внутренней логике:

1. первичный балл;  
2. максимальный балл;  
3. процент;  
4. уровень;  
5. результат по темам;  
6. ошибки;  
7. правильные ответы.

### **Режим ЦЭ/ЦТ**

В режиме ЦЭ/ЦТ нужно заложить возможность считать:

1. первичный балл;  
2. тестовый балл 0-100 по таблице соответствия, если шкала подключена;  
3. результат по темам;  
4. ошибки;  
5. правильные ответы.

Важно: нельзя называть результат официальным результатом ЦЭ/ЦТ. Формулировка должна быть:

“Тренировочный расчёт по таблице соответствия первичных и тестовых баллов.”

Подключение шкалы 0-100 можно реализовать в MVP или вынести в релиз 1.1, но архитектура должна быть заложена сразу.

## **7\. Основные бизнес-правила**

1. Один тест может быть создан вручную или через импорт Excel/CSV.  
2. После импорта вопросы можно редактировать вручную.  
3. Тест не виден ученикам, пока он не опубликован.  
4. Ученик может начать тест только при наличии активного доступа.  
5. Доступ может появиться после оплаты, ручной выдачи или активации одноразового кода.  
6. В первой версии ученик покупает один конкретный тест.  
7. В первой версии одна покупка даёт одну попытку.  
8. Количество попыток должно храниться как настройка, чтобы позже его можно было изменить.  
9. Срок доступа должен храниться как настройка теста.  
10. По умолчанию срок доступа: 7 дней.  
11. Попытка списывается при старте теста, а не при завершении.  
12. При старте попытки создаётся snapshot теста.  
13. После завершения теста ответы нельзя менять.  
14. Если время вышло, тест завершается автоматически.  
15. Результат считается только на backend.  
16. Правильные ответы нельзя отдавать ученику до завершения теста.  
17. Старые результаты не должны ломаться после редактирования теста.  
18. Одноразовый код доступа можно использовать только один раз.  
19. Администратор может вручную выдать доступ ученику.  
20. Администратор должен видеть оплаты, доступы и результаты.

## **8\. Публичная часть**

В MVP нужны страницы:

1. главная страница, если утверждена;  
2. каталог тестов;  
3. страница теста;  
4. экран ввода email;  
5. экран оплаты;  
6. экран успешной оплаты;  
7. экран ошибки оплаты;  
8. экран активации одноразового кода;  
9. экран перед началом теста;  
10. экран прохождения теста;  
11. экран подтверждения завершения;  
12. страница результата;  
13. служебные страницы ошибок доступа.

---

## **8.2. Каталог тестов**

Каталог должен показывать опубликованные тесты.

Карточка теста должна содержать:

1. название;  
2. предмет;  
3. краткое описание;  
4. режим теста;  
5. количество вопросов;  
6. время прохождения;  
7. количество попыток;  
8. цену;  
9. кнопку “Подробнее”.

Скрытые и черновые тесты в каталоге не показываются.

---

## **8.3. Страница теста**

Страница теста должна содержать:

1. название теста;  
2. предмет;  
3. описание;  
4. что проверяет тест;  
5. количество вопросов;  
6. время прохождения;  
7. количество попыток;  
8. срок доступа;  
9. цену;  
10. кнопку “Купить доступ”;  
11. кнопку или ссылку “У меня есть код”;  
12. правила прохождения.

---

## **8.4. Ввод email**

Перед оплатой ученик вводит email.

Поля:

1. email.

Проверки:

1. email обязателен;  
2. email должен быть валидным;  
3. email нужно нормализовать: trim, lowercase.

После ввода email система создаёт или находит пользователя с ролью student.

---

## **8.5. Оплата**

После ввода email ученик переходит к оплате.

В первой версии нужны способы:

1. банковская карта;  
2. ЕРИП;  
3. ручная выдача доступа через админку;  
4. одноразовый код доступа.

Платёжный провайдер пока не выбран. Нужно реализовать абстракцию, чтобы можно было подключить конкретного провайдера позже.

После успешной оплаты:

1. создаётся Payment со статусом success;  
2. создаётся Access;  
3. ученику отправляется email;  
4. ученик видит экран успешной оплаты;  
5. ученик может перейти к тесту.

Если оплата неуспешна:

1. Payment получает статус failed/cancelled;  
2. Access не создаётся;  
3. ученик видит экран ошибки оплаты.

---

## **8.6. Активация одноразового кода**

На сайте должен быть сценарий:

“У меня есть код”

Ученик вводит:

1. код;  
2. email.

Система проверяет:

1. код существует;  
2. код активен;  
3. код не использован;  
4. код не истёк;  
5. код не отозван;  
6. тест, к которому привязан код, существует;  
7. тест не удалён.

Если код валиден:

1. создаётся или находится ученик по email;  
2. создаётся Access;  
3. код помечается как used;  
4. сохраняется activated\_by\_user\_id;  
5. сохраняется activated\_at;  
6. ученик получает доступ к тесту.

Если код невалиден, показываем понятную ошибку.

---

## **8.7. Экран перед тестом**

Перед началом теста ученик видит:

1. название теста;  
2. количество вопросов;  
3. время прохождения;  
4. количество доступных попыток;  
5. правила прохождения;  
6. предупреждение, что попытка спишется после старта;  
7. кнопку “Начать тест”.

---

## **8.8. Прохождение теста**

Экран прохождения должен показывать:

1. номер текущего вопроса;  
2. общее количество вопросов;  
3. текст вопроса;  
4. варианты ответа или поле ввода;  
5. прогресс;  
6. таймер;  
7. кнопку “Назад”;  
8. кнопку “Далее”;  
9. кнопку “Завершить тест”.

Ученик может:

1. переходить назад;  
2. переходить вперёд;  
3. менять ответы до завершения;  
4. завершить тест вручную.

Если время вышло:

1. тест завершается автоматически;  
2. сохранённые ответы отправляются на проверку;  
3. пустые ответы считаются неправильными;  
4. результат показывается ученику.

---

## **8.9. Страница результата**

После завершения теста ученик видит:

1. первичный балл;  
2. максимальный балл;  
3. процент;  
4. уровень;  
5. результат по темам;  
6. список ошибок;  
7. правильные ответы;  
8. рекомендации по слабым темам.

Если включён режим ЦЭ/ЦТ и подключена шкала, дополнительно показывается:

1. тестовый балл 0-100;  
2. подпись, что это тренировочный расчёт.

Объяснения к вопросам необязательны. Если объяснения нет, пустой блок лучше не показывать.

---

## **8.10. Служебные состояния ученика**

Нужно предусмотреть состояния:

1. доступ не найден;  
2. доступ истёк;  
3. попытки закончились;  
4. доступ отозван;  
5. код не найден;  
6. код уже использован;  
7. код истёк;  
8. код отозван;  
9. оплата обрабатывается;  
10. оплата не завершена;  
11. тест скрыт;  
12. тест удалён;  
13. попытка уже завершена;  
14. время вышло.

10. результаты;  
11. настройки.

---

## **9.2. Вход в админку**

Администратор входит по email и паролю.

Требования:

1. пароль хранить в хэшированном виде;  
2. админские страницы доступны только авторизованному админу;  
3. ученик не может попасть в админку;  
4. после logout доступ закрывается.

---

Таблица тестов должна показывать:

1. название;

5. количество вопросов;  
6. цену;  
7. количество продаж;  
8. количество прохождений;  
9. дату обновления;

Действия:

1. открыть;  
2. редактировать;  
3. предпросмотр;  
4. опубликовать;

6. удалить, если безопасно.

Форма создания теста должна содержать:

1. название;  
2. subject;  
3. режим теста: training или ce\_ct;  
4. краткое описание;  
5. полное описание;  
6. цена;  
7. валюта;  
8. время прохождения;  
9. количество попыток;  
10. срок доступа;  
11. статус.

Кнопки:

1. сохранить черновик;  
2. сохранить и перейти к вопросам;  
3. отменить.

---

## **9.5. Редактирование теста**

Страница редактирования теста должна иметь вкладки:

1. основное;  
2. вопросы;  
3. импорт;  
4. предпросмотр;  
5. результаты;  
6. настройки доступа;  
7. настройки оценивания.

---

## **9.6. Вкладка “Вопросы”**

На вкладке вопросов нужно показывать:

1. количество вопросов;  
2. максимальный балл;  
3. список тем;  
4. предупреждения по качеству;  
5. список вопросов.

Кнопки:

1. добавить вопрос;  
2. импортировать из Excel/CSV;  
3. скачать шаблон;  
4. предпросмотр теста.

---

## **9.7. Список вопросов**

Список вопросов должен показывать:

1. номер;  
2. текст вопроса;  
3. тип вопроса;  
4. правильный ответ;  
5. тема;  
6. подтема;  
7. баллы;  
8. действия.

Действия:

1. редактировать;  
2. удалить;  
3. переместить вверх;  
4. переместить вниз.

Дублирование вопроса можно вынести в следующую версию.

---

## **9.8. Форма вопроса**

Форма вопроса должна поддерживать три типа:

1. single\_choice;  
2. multiple\_choice;  
3. short\_text.

Общие поля:

1. текст вопроса;  
2. тип вопроса;  
3. правильный ответ;  
4. тема;  
5. подтема;  
6. сложность;  
7. баллы;  
8. источник;  
9. объяснение.

Для single\_choice и multiple\_choice показываются варианты:

1. option\_a;  
2. option\_b;  
3. option\_c;  
4. option\_d.

Для short\_text варианты ответа не обязательны.

Кнопки:

1. сохранить;  
2. сохранить и добавить ещё;  
3. отменить.

---

## **9.9. Валидация вопроса**

Вопрос нельзя сохранить, если:

1. пустой текст вопроса;  
2. не выбран тип вопроса;  
3. не указан правильный ответ;  
4. не указана тема;  
5. не указаны баллы;  
6. баллы меньше или равны 0;  
7. для single\_choice правильный ответ не A/B/C/D;  
8. для single\_choice правильный ответ указывает на пустой вариант;  
9. для multiple\_choice правильные ответы не являются набором A/B/C/D;  
10. для multiple\_choice один из правильных ответов указывает на пустой вариант;  
11. для short\_text правильный ответ пустой.

Предупреждения, но не блокировка:

1. нет объяснения;  
2. нет подтемы;  
3. слишком длинный вопрос;  
4. возможный дубль вопроса;  
5. все вопросы теста из одной темы.

---

## **9.10. Импорт Excel/CSV**

Админ может загрузить файл с вопросами.

Требования:

1. поддержать XLSX;  
2. поддержать CSV;  
3. дать скачать шаблон;  
4. проверить структуру файла;  
5. проверить обязательные поля;  
6. показать ошибки;  
7. не импортировать файл с критическими ошибками;  
8. дать выбрать режим: добавить или заменить;  
9. после успешного импорта показать список импортированных вопросов.

---

## **9.11. Режимы импорта**

Если в тесте уже есть вопросы, при импорте нужно спросить:

“Как импортировать вопросы?”

Варианты:

1. добавить к текущим вопросам;  
2. заменить все вопросы.

По умолчанию:

добавить к текущим вопросам.

При выборе “заменить все вопросы” показать предупреждение:

“Текущие вопросы будут заменены вопросами из файла. Уже завершённые результаты учеников не изменятся.”

---

## **9.12. Предпросмотр теста**

Админ может посмотреть тест глазами ученика.

Предпросмотр:

1. не требует оплаты;  
2. не создаёт настоящую попытку;  
3. не списывает доступ;  
4. не попадает в результаты;  
5. показывает вопросы в том же виде, что ученик увидит в тесте.

---

## **9.13. Публикация теста**

Перед публикацией система должна проверить тест.

Тест нельзя опубликовать, если:

1. нет названия;  
2. нет цены;  
3. нет времени прохождения;  
4. нет срока доступа;  
5. нет вопросов;  
6. есть вопросы без правильного ответа;  
7. есть вопросы без темы;  
8. есть вопросы без баллов;  
9. включена шкала ЦЭ/ЦТ, но нет шкалы;  
10. максимальный первичный балл теста не совпадает со шкалой, если шкала включена.

Тест можно опубликовать с предупреждениями, если:

1. нет объяснений;  
2. нет подтем;  
3. мало вопросов;  
4. мало тем;  
5. нет полного описания.

---

## **9.14. Оплаты в админке**

1. дату оплаты;  
2. email ученика;

6. способ оплаты;  
7. статус оплаты;

Статусы оплаты:

1. pending;  
2. success;  
3. failed;  
4. cancelled;  
5. refunded.

---

## **9.15. Доступы в админке**

Раздел доступов должен показывать:

1. email ученика;  
2. тест;  
3. источник доступа;  
4. количество попыток всего;  
5. количество оставшихся попыток;  
6. срок действия;  
7. статус;  
8. дату создания.

Источники доступа:

1. payment;  
2. manual;  
3. access\_code.

Статусы доступа можно вычислять:

1. active;  
2. expired;  
3. used;  
4. revoked.

---

## **9.16. Ручная выдача доступа**

Форма ручной выдачи доступа:

1. email ученика;  
2. имя ученика, необязательно;  
3. тест;  
4. количество попыток;  
5. срок доступа;  
6. комментарий.

После создания:

1. найти или создать пользователя;  
2. создать Access;  
3. отправить email;  
4. записать лог.

---

## **9.17. Коды доступа**

В админке нужен раздел “Коды доступа”.

Админ может:

1. создать код;  
2. выбрать тест;  
3. указать количество попыток;  
4. указать срок действия кода;  
5. указать срок доступа после активации;  
6. добавить комментарий;  
7. увидеть сгенерированный код;  
8. скопировать код;  
9. видеть список кодов;  
10. видеть статус кода;  
11. отозвать код, желательно P1, но поле заложить сразу.

Код показывается админу после генерации. В базе нужно хранить не сам код, а hash.

---

## **9.18. Результаты в админке**

Раздел результатов должен показывать:

1. email ученика;  
2. тест;  
3. дату старта;  
4. дату завершения;  
5. длительность;  
6. статус попытки;  
7. балл;  
8. максимальный балл;  
9. процент;  
10. уровень;  
11. результат по темам.

Детальная страница попытки должна показывать:

1. вопросы;  
2. ответы ученика;  
3. правильные ответы;  
4. правильность;  
5. баллы по каждому вопросу;  
6. темы;  
7. подтемы.

---

## **10\. Типы вопросов**

## **10.1. single\_choice**

Один правильный ответ.

Поля:

1. question\_text;  
2. option\_a;  
3. option\_b;  
4. option\_c;  
5. option\_d;  
6. correct\_answer;  
7. topic;  
8. subtopic;  
9. points.

Правильный ответ:

A, B, C или D.

Проверка:

ответ ученика должен полностью совпадать с correct\_answer.

---

## **10.2. multiple\_choice**

Несколько правильных ответов.

Поля:

1. question\_text;  
2. option\_a;  
3. option\_b;  
4. option\_c;  
5. option\_d;  
6. correct\_answer;  
7. topic;  
8. subtopic;  
9. points.

Правильный ответ хранится как набор вариантов:

A,C,D

Проверка:

1. нормализовать порядок;  
2. сравнить выбранный учеником набор с правильным набором;  
3. если полное совпадение, начислить баллы;  
4. если не полное совпадение, начислить 0\.

Частичные баллы в MVP не делать.

---

## **10.3. short\_text**

Короткий текстовый ответ.

Поля:

1. question\_text;  
2. correct\_answer;  
3. topic;  
4. subtopic;  
5. points.

Correct answer может содержать несколько допустимых вариантов через разделитель:

пришёл;пришел

Проверка:

1. привести ответ ученика к нижнему регистру;  
2. убрать пробелы в начале и конце;  
3. сравнить с каждым допустимым вариантом;  
4. если есть совпадение, начислить баллы;  
5. если нет, начислить 0\.

В MVP не делать:

1. AI-проверку;  
2. морфологическую проверку;  
3. fuzzy matching;  
4. ручную проверку.

---

## **11\. Импорт Excel/CSV**

## **11.1. Поддерживаемые форматы**

Основной формат:

1. XLSX.

Дополнительный формат:

1. CSV.

Для CSV нужно поддержать UTF-8.

---

## **11.2. Колонки шаблона**

Файл импорта должен поддерживать колонки:

1. question\_text;  
2. question\_type;  
3. option\_a;  
4. option\_b;  
5. option\_c;  
6. option\_d;  
7. correct\_answer;  
8. topic;  
9. subtopic;  
10. difficulty;  
11. points;  
12. source;  
13. explanation.

---

## **11.3. Обязательные колонки**

Обязательные колонки:

1. question\_text;  
2. question\_type;  
3. correct\_answer;  
4. topic;  
5. points.

Для single\_choice и multiple\_choice дополнительно нужны варианты ответа.

Для short\_text варианты ответа не обязательны.

---

## **11.4. Правила валидации файла**

Критические ошибки:

1. нет обязательной колонки;  
2. пустой question\_text;  
3. пустой question\_type;  
4. неизвестный question\_type;  
5. пустой correct\_answer;  
6. пустой topic;  
7. пустой points;  
8. points не число;  
9. points меньше или равен 0;  
10. для single\_choice нет минимум двух вариантов ответа;  
11. для single\_choice correct\_answer не A/B/C/D;  
12. для single\_choice correct\_answer указывает на пустой вариант;  
13. для multiple\_choice нет минимум двух вариантов ответа;  
14. для multiple\_choice correct\_answer содержит не A/B/C/D;  
15. для multiple\_choice correct\_answer указывает на пустой вариант;  
16. для short\_text correct\_answer пустой.

Предупреждения:

1. нет explanation;  
2. нет subtopic;  
3. нет difficulty;  
4. возможный дубль вопроса;  
5. слишком длинный текст вопроса.

---

## **11.5. Частичный импорт**

Частичный импорт запрещён.

Если в файле есть критические ошибки, файл не импортируется.

Система должна показать список ошибок с указанием строки и причины.

---

## **12\. Оплата и доступ**

## **12.1. Payment**

Платёж создаётся после выбора теста и ввода email.

Статусы платежа:

1. pending;  
2. success;  
3. failed;  
4. cancelled;  
5. refunded.

После success создаётся Access.

Webhook оплаты должен быть идемпотентным: если webhook пришёл повторно, второй Access не создаётся.

---

## **12.2. Access**

Access даёт право пройти конкретный тест.

Access содержит:

1. user\_id;  
2. test\_id;  
3. payment\_id, если доступ создан оплатой;  
4. source;  
5. attempts\_total;  
6. attempts\_available;  
7. expires\_at;  
8. revoked\_at;  
9. created\_at.

Source:

1. payment;  
2. manual;  
3. access\_code.

---

## **12.3. Проверка доступа**

Перед стартом теста система проверяет:

1. пользователь существует;  
2. тест существует;  
3. доступ существует;  
4. доступ не отозван;  
5. срок доступа не истёк;  
6. есть доступные попытки;  
7. тест не удалён.

Если проверка не пройдена, старт теста запрещён.

---

## **12.4. Несколько активных доступов**

Если у ученика несколько активных доступов к одному тесту, при старте использовать доступ с ближайшим expires\_at.

---

## **12.5. Истечение доступа во время попытки**

Если доступ истёк после старта попытки, начатую попытку можно завершить.

---

## **13\. Одноразовые коды доступа**

## **13.1. AccessCode**

Одноразовый код создаётся администратором.

Поля:

1. id;  
2. code\_hash;  
3. test\_id;  
4. created\_by\_admin\_id;  
5. status;  
6. attempts\_total;  
7. access\_days;  
8. code\_expires\_at;  
9. activated\_by\_user\_id;  
10. activated\_at;  
11. created\_at;  
12. updated\_at;  
13. comment.

Статусы:

1. active;  
2. used;  
3. expired;  
4. revoked.

---

## **13.2. Активация кода**

Ученик вводит код и email.

Если код валиден:

1. создаётся или находится user;  
2. создаётся Access;  
3. Access получает source \= access\_code;  
4. код получает status \= used;  
5. сохраняется activated\_by\_user\_id;  
6. сохраняется activated\_at.

Повторная активация невозможна.

---

## **13.3. Безопасность кода**

Требования:

1. код должен быть достаточно длинным и случайным;  
2. в базе хранить hash кода;  
3. код показывать админу после генерации;  
4. при проверке сравнивать hash;  
5. код нельзя использовать после истечения срока;  
6. код нельзя использовать после отзыва;  
7. код нельзя использовать повторно.

---

## **14\. Попытка прохождения теста**

## **14.1. Attempt**

Попытка создаётся при нажатии “Начать тест”.

Статусы попытки:

1. started;  
2. completed;  
3. expired;  
4. cancelled.

При старте:

1. проверить доступ;  
2. создать Attempt;  
3. создать snapshot теста;  
4. списать попытку;  
5. сохранить started\_at;  
6. запустить таймер.

---

## **14.2. Snapshot**

Snapshot обязателен.

В snapshot нужно сохранить:

1. id теста;  
2. название теста;  
3. настройки теста;  
4. режим теста;  
5. настройки оценивания;  
6. список вопросов;  
7. порядок вопросов;  
8. типы вопросов;  
9. варианты ответов;  
10. правильные ответы;  
11. баллы;  
12. темы;  
13. подтемы;  
14. объяснения, если есть.

Правильные ответы находятся в snapshot, но не отдаются ученику до завершения.

---

## **14.3. Сохранение ответов**

Ответы ученика нужно сохранять во время прохождения.

Для каждого ответа хранить:

1. attempt\_id;  
2. question\_id или snapshot\_question\_id;  
3. selected\_answer;  
4. timestamp.

После завершения теста ответы нельзя менять.

---

## **14.4. Завершение попытки**

Попытка завершается:

1. вручную учеником;  
2. автоматически по таймеру.

После завершения:

1. попытка получает статус completed или expired;  
2. считаются баллы;  
3. считаются темы;  
4. формируются рекомендации;  
5. результат становится доступен ученику и админу.

---

## **15\. Расчёт результата**

## **15.1. Базовая формула**

Считаем:

1. raw\_score \= сумма баллов за правильные ответы;  
2. max\_score \= сумма максимальных баллов всех вопросов;  
3. percent \= raw\_score / max\_score \* 100\.

---

## **15.2. Уровни**

Рекомендованная шкала уровней:

1. 0-39% \- низкий;  
2. 40-59% \- ниже среднего;  
3. 60-79% \- средний;  
4. 80-89% \- хороший;  
5. 90-100% \- высокий.

---

## **15.3. Результат по темам**

Для каждой темы считать:

1. topic\_score;  
2. topic\_max\_score;  
3. topic\_percent.

Статусы тем:

1. 0-59% \- слабая тема;  
2. 60-79% \- требует повторения;  
3. 80-100% \- нормально.

---

## **15.4. Рекомендации**

Рекомендации формируются без AI.

Алгоритм:

1. найти темы с результатом ниже 60%;  
2. найти ошибочные вопросы в этих темах;  
3. взять подтемы, если они указаны;  
4. убрать дубли;  
5. показать 3-5 тем или подтем для повторения.

Если слабых тем нет, показать нейтральную рекомендацию:

“Серьёзных слабых тем не найдено. Рекомендуем повторить вопросы, в которых были ошибки.”

---

## **15.5. CE/CT scoring**

Если включён режим ЦЭ/ЦТ и подключена шкала:

1. посчитать raw\_score;  
2. найти scaled\_score по таблице соответствия;  
3. показать scaled\_score ученику.

Если raw\_score не найден в шкале:

1. показать raw\_score;  
2. не показывать scaled\_score;  
3. залогировать ошибку;  
4. показать сообщение, что тестовый балл временно недоступен.

---

## **16\. Email-уведомления**

В MVP нужны email:

1. после успешной оплаты;  
2. после ручной выдачи доступа;  
3. после активации кода, желательно;  
4. после завершения теста, желательно.

Минимально обязательно:

1. email после успешной оплаты;  
2. email после ручной выдачи доступа.

Email после оплаты должен содержать:

1. название теста;  
2. ссылку на тест;  
3. срок доступа;  
4. количество попыток.

## **19\. Нефункциональные требования**

## **19.1. Адаптивность**

Сервис должен корректно работать на:

1. desktop;  
2. tablet;  
3. mobile.

Мобильная адаптация обязательна, потому что ученики могут проходить тесты с телефона.

---

## **19.2. Производительность**

MVP должен без проблем поддерживать:

1. 1-3 теста на старте;  
2. десятки/сотни учеников;  
3. одновременное прохождение несколькими пользователями;  
4. импорт файлов с десятками/сотнями вопросов.

---

## **19.3. Безопасность**

Требования:

1. админка защищена авторизацией;  
2. пароли админов хранятся в hash;  
3. ученик не может видеть чужие результаты;  
4. ученик не может начать тест без доступа;  
5. правильные ответы не отдаются до завершения;  
6. webhook оплаты проверяется;  
7. одноразовые коды хранятся в hash;  
8. действия админа по ручной выдаче доступа логируются;  
9. критические операции выполняются на backend;  
10. результат считается только на backend.

---

## **19.4. Надёжность**

Нужно предусмотреть:

1. повторный webhook не создаёт второй доступ;  
2. обновление страницы во время теста не создаёт новую попытку;  
3. начатая попытка продолжается после перезагрузки;  
4. таймер считается от started\_at на backend;  
5. старые результаты не ломаются после изменения теста;  
6. импорт с ошибками не создаёт частичный мусор;  
7. код доступа нельзя активировать дважды.

---

## **19.5. Логирование**

Нужно логировать:

1. создание теста;  
2. публикацию теста;  
3. импорт вопросов;  
4. ошибки импорта;  
5. успешные оплаты;  
6. ошибки webhook;  
7. ручную выдачу доступа;  
8. создание кода доступа;  
9. активацию кода;  
10. старт попытки;  
11. завершение попытки;  
12. ошибки расчёта результата.

## **20\. Критерии готовности MVP**

MVP считается готовым, если:

1. админ может войти в админку;  
2. админ может создать тест;  
3. админ может добавить вопросы вручную;  
4. админ может создать вопросы типов single\_choice, multiple\_choice, short\_text;  
5. админ может импортировать вопросы из Excel/CSV;  
6. система показывает ошибки в файле;  
7. админ может выбрать режим импорта: добавить или заменить;  
8. админ может отредактировать вопросы после импорта;  
9. админ может запустить предпросмотр теста;  
10. админ может опубликовать тест;  
11. ученик видит опубликованный тест в каталоге;  
12. ученик может открыть страницу теста;  
13. ученик может ввести email;  
14. ученик может оплатить тест;  
15. после успешной оплаты создаётся доступ;  
16. ученик может активировать одноразовый код;  
17. после активации кода создаётся доступ;  
18. админ может вручную выдать доступ;  
19. ученик может начать тест только при активном доступе;  
20. попытка списывается при старте;  
21. при старте создаётся snapshot теста;  
22. ученик может отвечать на вопросы;  
23. ученик может менять ответы до завершения;  
24. таймер работает корректно;  
25. тест завершается вручную или автоматически;  
26. результат считается автоматически;  
27. ученик видит баллы, процент, ошибки и правильные ответы;  
28. ученик видит результат по темам;  
29. админ видит оплаты;  
30. админ видит доступы;  
31. админ видит результаты учеников;  
32. старые результаты не ломаются после редактирования теста.

## **22\. Рекомендованный стек**

Рекомендованный стек для MVP:

1. Next.js для frontend и backend API;  
2. PostgreSQL как база данных;  
3. Prisma как ORM;  
4. готовый провайдер оплаты после выбора;  
5. библиотека для XLSX/CSV импорта;  
6. email-сервис для отправки писем;  
7. хостинг, поддерживающий backend и PostgreSQL.

Альтернативный стек для более сложной архитектуры:

1. Next.js frontend;  
2. NestJS backend;  
3. PostgreSQL;  
4. Prisma;  
5. отдельный worker для email/import, если понадобится.

Для MVP предпочтительнее не усложнять архитектуру без необходимости.

## **23\. Итоговое описание первой версии**

Нужно разработать MVP веб\-сервиса, где преподаватель может создавать тесты по русскому языку вручную или через Excel/CSV, публиковать их и выдавать/продавать доступ ученикам.

Ученик может получить доступ через оплату, ручную выдачу или одноразовый код, пройти тест онлайн и сразу получить результат с баллами, ошибками, правильными ответами и темами.

Первая версия должна быть небольшой, но полностью рабочей коммерческой системой: создать тест, выдать доступ, пройти тест, получить результат, увидеть данные в админке.
