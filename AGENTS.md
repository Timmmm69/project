## Scope MVP

MVP - веб-сервис для продажи онлайн-тестов по русскому языку для подготовки к ЦЭ/ЦТ.

Главная цепочка MVP:

преподаватель создает тест -> ученик получает доступ через оплату, ручную выдачу или код -> проходит тест -> получает результат -> преподаватель видит оплаты, доступы, коды и результаты.

## Обязательные технические правила

- Scoring считается только на backend.
- Правильные ответы нельзя отдавать ученику до завершения попытки.
- Access можно создать только после подтвержденной оплаты, ручной выдачи админом или валидного одноразового кода.
- AccessCode нельзя хранить в базе открытым текстом; хранить только hash.
- Повторный payment webhook не должен создавать второй Access.
- Обновление страницы во время теста не должно списывать вторую попытку.
- Snapshot обязателен при старте попытки.
- Старые результаты не должны ломаться после редактирования теста или вопросов.
- Критические операции должны выполняться в transaction.
- Email-ошибка не должна ломать создание Access.

## Приоритеты реализации

Рабочий порядок описан в `docs/08-execution-master-plan.md`. Пользователь утверждает approval gates и спорные решения; Codex выполняет подготовку, реализацию, проверки и обновление документации.

1. Сначала структура проекта и документация.
2. Затем база проекта, Prisma и admin auth.
3. Затем тесты и вопросы.
4. Затем импорт.
5. Затем публичная часть.
6. Затем оплаты, доступы и коды.
7. Затем попытки, snapshot и timer.
8. Затем scoring, шкала ЦЭ/ЦТ 0-100 и результаты.
9. Затем QA и запуск.

## Как работать с модулями

После каждого модуля Codex обязан кратко написать:

- что сделано;
- как проверить;
- какие риски остались;
- какие решения требуют утверждения.

Если решение влияет на архитектуру, деньги, безопасность или scope, Codex должен дать 2-3 варианта с плюсами и минусами и дождаться утверждения.

## Проверки перед завершением задачи

Для каждого изменения нужно проверить релевантный минимум:

- `pnpm lint`, если настроен;
- `pnpm test`, если есть тесты;
- `pnpm typecheck`, если TypeScript-проект уже создан;
- ручную проверку сценария, если автоматические тесты еще не готовы.

Если проверку выполнить нельзя, нужно явно указать причину.
